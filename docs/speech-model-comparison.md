# 예약 통역에 쓸 음성 인식 모델과 시간 정렬

사용자가 마이크로 “두 명 예약하고 싶습니다”라고 말했을 때 화면에는 “오늘의 드론 예약하고 싶습니다”라고 표시된 적이 있습니다.
번역 모델은 음성 인식기가 받아쓴 글을 번역합니다.
인원이 잘못 전달됐다면 먼저 화면의 원문에 “두 명”이 맞게 적혔는지 확인하세요.

2026년 11월 15일, 통합 메모리가 48 GiB인 M4 Pro에서 Whisper small로 한국어 합성 음성 세 문장을 확인하고 다른 음성 인식 모델의 공개 사양을 조사했습니다.
후보들을 같은 녹음으로 실행해 정확도나 속도를 비교하는 실험은 아직 하지 않았습니다.
11월 16일 웹 앱과 통역 제어기를 Go로 옮긴 뒤에도 음성 인식 모델은 Whisper small을 사용합니다. [현재 시스템 구조](../README.md#전체-시스템-구조) · [통역 사양](../SPEC.md)

## 정렬 모델이 하는 일

음성 인식기(ASR)는 녹음을 받아씁니다.
강제 정렬 모델(forced aligner)은 녹음과 전사문을 함께 받아 **어느 단어를 언제 말했는지** 추정합니다.
Qwen3-ForcedAligner가 지원하는 언어에는 한국어와 일본어가 모두 포함됩니다. [Qwen 모델 설명](https://huggingface.co/Qwen/Qwen3-ForcedAligner-0.6B)

| 구성 요소 | 입력 → 출력 | 우리 앱에서의 역할 |
| --- | --- | --- |
| 음성 인식(ASR) | 오디오 → 원문 텍스트 | 무슨 말을 했는지 인식 |
| 시간 정렬 | 오디오 + 전사문 → 단어/글자의 시작·끝 시간 | 확정한 텍스트가 오디오의 어디까지인지 찾음 |
| 번역 시점 판단(Gemma) | 현재 원문과 필요한 이전 문맥 → R 또는 W | 의미가 완결됐는지 판단 |
| 번역 | 원문 → 상대 언어 텍스트 | 점원의 한국어 자막 또는 사용자 답변의 일본어 번역 생성 |

한 번의 녹음에 두 문장이 들어왔다고 가정해 보겠습니다.
아래 시간은 원리를 설명하기 위한 예시입니다.

```text
오디오 시간   0.0s                 1.4s                    3.0s
             |--------------------|------------------------|
원문         [두 명입니다.]        [저녁 일곱 시예요.]
                       ^ 정렬 결과: 첫 문장 끝이 약 1.4초

ASR:         "두 명입니다. 저녁 일곱 시예요."
Gemma:       "두 명입니다."의 의미 완결 확인
남은 녹음:   [확정한 부분은 덜어냄] [다음 번역을 위해 남김]
```

첫 문장인 “두 명입니다”를 번역한 뒤에는 녹음의 처음 1.4초만 덜어내야 “저녁 일곱 시예요”까지 이어서 번역할 수 있습니다.
녹음 전체를 비우면 뒷말을 잃고, 처음부터 다시 보내면 같은 말을 두 번 번역할 수 있습니다.

시간 정렬에는 인식기가 받아쓴 문장이 그대로 들어갑니다.
“두 명”을 “오늘의 드론”이라고 받아썼다면 정렬 모델은 잘못 적힌 말의 위치를 찾으려 합니다.
원문 오류는 인식 단계에서 확인해야 합니다.
단어 경계 역시 추정값이므로, 앞 문장을 잘랐을 때 뒷말이 남아 있는지 실제 녹음으로 확인해야 합니다.

## 현재 Whisper 경로와 Qwen 후보의 차이

현재 연속 통역 화면(`/live`)은 whisper.cpp가 인식한 토큰의 시간 정보를 요청합니다.
통역 제어기는 이 정보로 어느 오디오 구간까지 처리했는지 추적합니다.
별도의 정렬 모델을 실행할 필요가 없습니다.

```text
현재 구현

오디오 -> Whisper small -> 원문 + 토큰 시간
                              |         |
                              |         +--> 녹음을 덜어낼 위치
                              +------------> 안정화 + Gemma R/W

Qwen 후보를 시험할 때 검토할 구성

오디오 -> Qwen3-ASR -> 원문 -> 안정화 + Gemma R/W
  |                      |
  +----> ForcedAligner <--+
                  |
                  +--> 단어 시간 -> 녹음을 덜어낼 위치
```

Go 제어기는 번역할 구간의 마지막 글자를 Whisper 토큰의 끝 시각과 맞출 수 있을 때만 그 구간을 확정합니다.
원문 전체를 확정했고 700 ms 이상 조용했다면 마지막 토큰 뒤의 무음까지 덜어냅니다. [음성 인식](../internal/speech/server.go) · [통역 세션](../internal/interpreter/session.go) · [구간 선택](../internal/interpreter/segment.go)

조사 당시 Qwen의 MLX 구현은 실시간 인식 결과에 단어별 시간을 붙이지 않았습니다.
문서에서는 단어 위치가 필요하면 강제 정렬 모델을 함께 쓰도록 안내합니다.
Qwen을 연속 통역에 연결하려면 받아쓴 글을 표시하는 일에 더해, 어느 지점까지 녹음을 덜어낼 수 있는지도 검증해야 합니다.
녹음을 끝낸 뒤 문장 전체를 번역하는 연습 모드에서는 그 경계를 찾을 필요가 없습니다. [MLX 구현의 스트리밍과 시간 정렬 설명](https://github.com/Neywa-Labs/mlx-audio/blob/main/mlx_audio/stt/models/qwen3_asr/README.md)

| 정렬 모델 조사 | Qwen3-ForcedAligner 0.6B, MLX 8-bit | 공개 문서에서 용도와 지원 언어, 가중치 크기를 확인했습니다. 이 Mac에서의 정렬 오차와 메모리 사용량은 아직 측정하지 않았습니다. |

Qwen3.5와 Qwen3.8의 기존 결과는 텍스트 번역 실험에서 얻었습니다.
Qwen3-ASR이 음성을 얼마나 잘 알아듣는지는 같은 녹음을 각 인식기에 들려준 뒤 전사문을 비교해야 알 수 있습니다.

아래는 11월 15일에 Whisper small이 합성 음성을 받아쓴 결과입니다.

| 합성 입력 | Whisper small 응답 | 음성 인식 처리 시간 |
| --- | --- | ---: |
| 두 명 예약하고 싶습니다. | 두 명 예약하고 싶습니다. | 171 ms |
| 두 명이요. | 2명이요. | 190 ms |
| 두 명이 아니라 네 명입니다. | 2명이 아니라 4명입니다. | 120 ms |

당시에는 macOS Yuna로 분당 180단어 속도의 음성을 만든 뒤 16 kHz 모노 PCM16으로 변환했습니다.
이를 한국어로 지정한 `/transcribe`에 보냈고, 인식 설정은 `reservation-asr-v1`이었습니다.
표의 시간은 각 요청의 음성 인식 처리 시간입니다.
녹음·전송·번역·재생에 걸린 시간은 포함하지 않았습니다.
입력 WAV와 원본 JSON은 보관하지 않아 당시 터미널에서 관찰한 값만 남아 있습니다.

세 합성 문장에서는 인원수가 유지됐지만 사용자가 보고한 “오늘의 드론” 오류는 재현되지 않았습니다.
당시의 마이크 녹음과 장치, 주변 소음을 확인할 수 없어 오류가 생긴 원인은 아직 알 수 없습니다.

## 측정한 메모리와 예상 예산

Gemma 26B 4비트로 텍스트를 처리한 실험에서 MLX가 할당한 메모리는 최대 **13.575 GiB**였습니다.
당시에는 음성 인식기를 함께 실행하지 않았습니다. [MLX 측정 기록](../benchmark/models.md)

11월 25일에는 Whisper small과 Gemma 26B GGUF로 짧은 대화를 통역하면서 두 프로세스의 상주 메모리(RSS)를 합산했습니다.
Whisper가 실행되는 Go 앱과 llama-server의 합계는 최대 14.997 GiB였습니다.
브라우저와 다른 앱은 측정에서 제외했습니다.
Qwen3-ASR과 정렬 모델을 함께 띄웠을 때의 사용량은 아직 측정하지 않았습니다. [앱에서 측정한 메모리](../benchmark/resources.md)

다른 앱을 함께 쓰면서 AI에 24 GB 또는 36 GB까지 배정할 수 있다고 가정했습니다.
아래 표는 그중 **36 GB를 어떻게 나눠 쓸지** 계산한 예시입니다.
1 GiB는 약 1.074 GB이므로 GB 단위 예산과 GiB 단위 실측값은 단위를 맞춰 비교해야 합니다.

| 항목 | 예약할 예산 | 근거/한계 |
| --- | ---: | --- |
| Gemma와 해당 런타임 | 18 GB | MLX 실측 약 14.6 GB에 여유를 둔 값. 프로세스 전체 사용량은 별도 측정 |
| Qwen ASR + 필요 시 정렬 + 런타임 | 8 GB | 두 모델의 공개 파일 합계가 약 3.73 GB여서 잡은 초기 추정치 |
| 웹 서버·오디오 버퍼 등 | 2 GB | 서버와 오디오 버퍼에 남겨 둔 예상치 |
| AI용 여유 메모리 | 8 GB | 동시에 실행할 때의 최대 사용량을 보고 조정 |
| 합계 | 36 GB | 운영체제와 다른 앱의 사용량은 별도 |

| AI 예산 | 당시 논의의 판단 | 아직 필요한 확인 |
| --- | --- | --- |
| 24 GB 정도 | Gemma와 Qwen 1.7B를 함께 시험하되 다른 앱을 위한 여유가 있는지 확인 | 프로세스 전체 사용량, 정렬 모델 사용 여부, 동시 실행 시 스왑 |
| 36 GB 정도 | Gemma, Qwen 1.7B 8-bit, 정렬 모델을 동시에 띄우는 실험의 예상 예산 | 실행 중 최대 사용량과 인식 시간, 다른 앱이 차지하는 메모리 |

두 언어의 입력을 한 음성 인식 모델로 처리하는 구성을 먼저 검토합니다.
후보는 하나씩 불러와 비교합니다.
당시 MLX 기반 Whisper 서버의 할당 설정은 4 GiB였습니다.
현재 앱에서 whisper.cpp만 차지하는 메모리는 별도로 측정해야 합니다.

## 다음 실험에서 측정할 항목

사용자가 비교용으로 제공한 동일한 녹음을 각 후보에 들려줍니다.
실제 마이크 입력은 동의 없이 자동 저장하지 않습니다.
합성 음성으로 먼저 연결을 확인한 뒤 실제 화자의 발음이나 주변 소음이 있는 조건을 따로 시험합니다.

| 평가 대상 | 비교할 내용 |
| --- | --- |
| ASR 원문 | 인원·날짜·시간·이름·부정·정정 보존, 삽입/누락, 한국어·일본어 글자 오류율(CER) |
| 점진적 인식 | 첫 잠정 결과 지연, 수정 빈도, 안정된 구간까지의 시간 |
| 시간 정렬 | 단어 경계 오차, 미정렬 구간, 뒤 음성 누락·중복 여부 |
| 메모리 | 모델을 불러올 때와 짧은 입력·최대 길이 입력을 처리할 때의 메모리. MLX 할당량과 프로세스 전체 사용량은 따로 기록 |
| 전체 경로 | Gemma 동시 부하, 큐 대기, 의미 확정·번역·음성 재생까지의 지연 |

실험마다 날짜와 녹음 파일의 해시, 사람이 확인한 전사문, 모델 버전·양자화 방식·실행 환경·프롬프트를 기록합니다.
인식기는 음성만 받고, 정렬 모델에는 인식기가 실제로 돌려준 전사문을 보냅니다.
인식 결과와 단어 경계는 각각 평가하고, 원본 응답과 실패 사례, 메모리 사용량도 함께 남깁니다.
